Reducing & Explaining SDK Startup Outliers

Recommendations derived from the four-device startup investigation (1,850+ instrumented cold starts, causal experiments; evidence in the external-factors summary and testing log). Two halves: engineering changes that shrink outlier frequency/severity, and a prod telemetry spec that explains why any given init was slow — without perfetto. Work items ranked by impact live in the companion tracking doc (linked in the footer).

Reviewed 2026-08-26 against SDK 9.2.0. Two changes: M7 was added — the OTel engine alternative, worth 15–20% of the window on mid and entry tiers, which is the largest measured lever here and had been missing from this page; and M1 was re-anchored to 9.2.0, where the config decode remains the largest single item in the window even though 9.2.0's own big win came from elsewhere in config handling. Where a figure was measured on an earlier build it now says so, rather than referring to an undated "HEAD".

Design principle from the findings: SDK init is memory-bound work exposed to environmental interference. Every mitigation either shrinks the window (a smaller target for GC bursts, dexopt storms, and thermal states to hit) or shrinks its memory appetite (less damage per hit). Everything we can't prevent, the telemetry must classify.

Part 1 — Reducing outlier frequency and severity

M1 · Make the persisted-config decode faster and overlap it17–28% of window at 9.2.0

Why: the binary config decode (EmbraceBinary.decodeFromStream) is CPU-bound main-thread work — pointer-chasing deserialization, so maximally interference-sensitive — and it is the largest remaining single item in the window. Still true at 9.2.0, and now located precisely: emb-persisted-config-load costs 6.0 ms (Pixel 3), 13.0 (A14) and 20.8 (A01 Core), and is the largest single direct child of the biggest in-window phase on every device measured — on the A01 Core it alone is 22% of the whole composed window. Note that 9.2.0's own large win came from a different part of config handling (config-service-init fell 84–93%); the decode itself did not go away, which is why this item survives that release rather than being closed by it.

Constraint (confirmed): the load is on the hot path by design — the rest of the SDK depends on its result — so it cannot be removed or deferred past its consumers. The levers are speed and overlap, not removal:

How: (a) overlap — start the decode on a background thread at class-load time (the embrace-impl-init/bootstrapper-init phase runs 2–11 ms before the window opens) and join at the top of modules-init; on most devices the decode finishes inside work that already happens, shrinking its critical-path cost toward zero without moving it off the hot path. (b) faster — trim the decoded payload to what init consumes, avoid transient allocation in the decode (also serves M4). (c) if (a)+(b) still leave low-end paying, a split init-critical mini-record is the structural escalation.

M2 · Baseline profile — VERIFIED highly effective, tails most of alldone 2026-08-12 · −44–52% worst-case

Result (measured 2026-08-12 on the then-current 9.2.0-era build, all four devices, CompilationMode.None vs Partial(Require), 2×20 per arm): window p50 −42 to −47% and max −47 to −52% on A14 / A01 / P7P — the A01's worst window halved (263 → 125 ms), the A14's p95 dropped 55 ms, and first-post-install launches improved proportionally (A14 iter000: 85/75 → 50/36 ms). The apparent exception was retired by better methodology: the Pixel 3 / Android 12 "inversion" did NOT survive a properly counterbalanced ABBA re-test (2026-08-13) — boundary deltas of +5.0% and −6.8% (opposite signs), noise-dominated. On ART 12 the profile is neutral: no benefit, no reliable penalty; the earlier +43%→+23% estimates were ordering/thermal bias (the counterbalancing lesson is in the multi-device skill's methodology). The recommendation is therefore unconditional fleet-wide. Bonus finding (X2, same night): Play installs apply cloud profiles at install time (install-dm), and Samsung's SPEG applies local ones — so the profile-compiled state is the prod norm on Play-delivered devices, making the profile arm the prod-representative benchmark arm.

Why it was ever doubted: the benchmark's default CompilationMode resets to fresh-install (verify) state, which never exercises the packaged profile — a with/without comparison run in default mode measures nothing, silently. The prior "no impact" conclusion is considered invalid.

Follow-on (benchmarking half IMPLEMENTED in both skills 2026-08-12): standard runs are now two-arm (default + Partial(Require)) with arm-cooling discipline; no-AOT stays as the coverage canary. Remaining: treat profile delivery/coverage as a first-class outlier mitigation for the entry tier — it is the largest single verified lever found by this investigation.

M3 · SDK background-work scheduling — judged by TOTAL app-startup impact, not window attributionneeds TTID-based experiment

The honest framing (per review): deferring our background work past the window improves the SDK-attributed number but the work still happens during app startup — that's moving cost to where it's harder to trace back to the SDK, not removing it. The real goal is minimizing total app-startup impact, so any change here must be judged by TTID/TTFD deltas, not window deltas.

Where deferral is legitimately a win: (a) work that can move past first-frame entirely (post-TTID idle) leaves the user-visible path; (b) on little-core devices, two memory-bound threads can be slower in total than the same work run sequentially (bandwidth contention is superlinear there) — so de-overlapping can reduce TTID itself, not just re-attribute it. Neither is assumed: the experiment is defer-vs-overlap variants measured by TTID on the A14 and P7P. If TTID is flat, the only defensible change is moving genuinely post-startup work (e.g. config fetch) past first-frame.

M4 · Init-path allocation budgetlow-RAM tier

Why: on the 1 GB Go device the app's own GC ran 64–99 ms inside half the outlier windows — init-time allocation crosses GC thresholds tiny heaps can't absorb.

How: streaming decode with reused buffers; avoid large transient allocations in the window; add an allocation regression check (Debug.getRuntimeStat GC counts around init in integration tests).

M5 · Minimize block-and-resume patterns in the windowcode audit in flight

Why: the sections that inflate ~2× under every adverse condition (config-service-init, payload-source-init, essential-service-init, post-init, delivery-init) share the short-section/resume-sensitive profile — each resume pays cache refill against whatever contaminated the caches.

Audit complete — concrete sites identified (full list with file:line in the plan doc, 2026-08-11-startup-outlier-investigation-plan.md): (1) a keyValueStore SYNCHRONIZED-lazy handoff where the main thread can park unboundedly on the config-HTTP worker's monitor — the top-ranked cause, with the race probability rising exactly with CPU pressure; (2) first-use worker thread creation (pthread_create parks the caller) inside three of the five inflating sections; (3) SharedPreferences prewarm/first-read waits landing in two unattributed sections (quick win: add recordDuration); (4) the post-init compound (monitor + prefs read-modify-write + thread start + first span's class loading). Notable exonerations: zero explicit blocking primitives on the path, binder-clean by default, and delivery-init/essential-service-init inflate from cold class-loading, not waits — pointing those two at the baseline profile (M2) instead. The audit also flagged EmbTrace's per-section atrace write() syscalls as a small per-section overhead under tracing — a real (minor) measurement cost, though its candidate role as the A14 pass-toggle explanation was refuted by E15 (the toggle is Samsung install-time compile-state alternation; see the testing log).

M7 · Switch the OTel engine to the Kotlin implementation15–20% of window on mid + entry tiers · measured, gated on correctness

Added 2026-08-26 — this is the largest measured lever on this page and it was missing from it. Assembling the OpenTelemetry engine is the single biggest phase of init at 9.2.0 (33–34% of the window on every device measured). The SDK can build it on either an OTel Java implementation or a Kotlin one, and 9.2.0 ships the Java-backed path by default.

Result (fleet A/B, two worktrees differing only in the config flag, 12 ABBA-mirrored legs × 20 launches per device, zero failed legs): A14 −9.20 ms / −20.4% (CI [−17.07, −2.53], p = 0.022), Pixel 3 −5.30 ms / −17.7% ([−5.43, −4.95], p = 0.003), A01 Core −14.54 ms / −15.1% ([−18.90, −10.97], p = 0.002). The flagship gains only −0.50 ms / −4.3%, and the reason is instructive rather than disappointing: the saving tracks the absolute size of the work removed, and total OTel construction spans 4.4 ms on the flagship to 59.3 ms on the Go device. An earlier flagship-only measurement concluded "minor lever" and was wrong by fourfold — ranking a fleet-wide change from the one device with nothing left to remove.

Why it is not simply done: the performance case is settled; correctness is not. Export parity, processor contracts and the remote-rollout path are unvalidated, which is why the flag is off. Two open measurement gaps before any default flip: the A/B measured medians only, so the tail is unquantified — a re-run preserving per-launch windows is in flight — and static verification that the two arms differ is weak (Android builds are not byte-reproducible), so the run's own median reproducing the figures above is what will confirm the flag took effect.

M6 · Accept-and-classify for the rest

Scheduler placement, other apps' dexopt, system_server GC, and device temperature are genuinely outside anyone's control. The available win is attribution (Part 2), plus prod methodology: segment version_startup_counter == 1 as its own cohort before any outlier analysis or alerting.

Part 2 — Prod telemetry: explaining slow inits without perfetto

Pattern: snapshot cheap counters at window start and end (raw bytes, ~tens of µs per read), compute deltas on a background thread after init, attach as attributes on the sdk-init span next to the existing per-section durations. Feature-detect readability once per device and cache (some vendors SELinux-block nodes that are world-readable by mode — every reader needs a silent fallback). Target <1 ms total main-thread cost.

Startup-cost classification (per review request): none = gathered after startup on a background worker (the signal varies slowly enough that post-window capture is valid); negligible = on-path but <0.1 ms even on slow devices; significant = can reach ≥0.1 ms on slow devices, needs a mitigation or a deliberate decision.

Shipped state (2026-08-13, committed & PRs in review): every row above except core placement and compile state is implemented. On-path cost as built: 4 tiny raw-byte procfs reads + 2 clock syscalls + 2 runtime-stat reads per init ≈ 0.15–0.4 ms worst-case on the slowest tier; everything marked none runs on the span-record worker and is memoized. All attribute keys live in one place — SdkInitAttributeKeys — as future semantic-convention candidates (deliberately not registered yet); the producers are SdkInitResourceUsageTracker (window deltas, captureStart/captureEnd) and sdkInitEnvironmentAttributes() (record-time snapshot).

The dashboard story this enables: every slow init classifies into pressured · thermal · IO-stalled · memory-pressured · mis-placed · first-launch · unexplained. The unexplained residual is the health check on the model itself. Regression alerting runs on the quiet cohort (low pressure, thermal_status 0, not first-launch) so environmental noise never masquerades as an SDK regression.

Validation before trusting it: two stages. (1) Presence: the four-device attr-presence sweep (runs tonight, 2026-08-13) verifies every attribute actually appears on real payloads across API 29–35 — SELinux/vendor gaps become findings, not silent holes. (2) Accuracy (P6): one bench campaign grading attribute classifications against perfetto ground truth — we already know exactly which iterations were GC-hit, dexopt-hit, hot, and mis-placed. The core pair is already device-validated (dose–response + accounting closure).
