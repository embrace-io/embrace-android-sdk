Reading the breakdown

Two costs dominate the span: span-service-init (40.1%), which is almost entirely its child otel-tracer-init (31.3%) — the first touch of the OTel SDK assembly (tracer provider, resource, processors); and persisted-config-load (27.9%) — the cached-config read, as usual the most variable section (3.1–16.9 ms). Everything else is ≤ 7% each. This pass ran on a cool device and reproduces the reference shape almost exactly (modules-init ~34.6 vs ~34, span-service-init ~15.0 vs ~15.5, persisted-config-load ~10.4 vs ~10, otel-tracer-init ~11.7 vs ~12), so the measurement is stable and there is no regression signal.

Cool vs. hot: the six-pass variance campaign

To test the earlier "warm passes inflate uniformly — thermal" hypothesis, the same benchmark ran five more times back-to-back on the same device (battery temperature sampled around each pass). The result kills the hypothesis: pass medians alternate — 37.5 → 50 → 39 → 48 → 39 → 50 ms — while temperature stays flat at 30–31 °C, and the inflation is not uniform across sections.

Where the slow passes lose their time: scheduling, not clocks

Comparing a slow iteration (57 ms span, pass 4 iter 000) against a fast one (35 ms, pass 4 iter 018) in their perfetto traces, over the emb-modules-init window on the main thread:

The slow run's extra ~20 ms is dominated by runnable-but-preempted time (14.8 ms) plus constant core migration — the actual CPU work grows only ~17% (36.3 vs 31.0 ms). The whole SoC is busy in the slow window: the top competing threads are system_server's HeapTaskDaemon (GC, 43.6 CPU-ms) and Play Store's stall_source.db (33.8 CPU-ms), plus binder and surfaceflinger threads. All 8 cores report the same 2.0 GHz ceiling and battery temperature never moved, so this is scheduler contention from install-triggered background work (each benchmark pass reinstalls the APK), not thermal throttling. That also explains the section skew: long uninterrupted CPU bursts (otel-tracer-init) keep their core, while sections that repeatedly block and re-queue pay the runnable-wait tax on every resume. One refinement from analyzing all 20 pass-5 traces: slow passes come in a second signature too — pass 5's iterations show near-zero wait but elevated Running time (43–59 ms vs ~31 ms on fast passes), i.e. the same work consuming more CPU-time (core placement/clocks) rather than queueing. Practical takeaway: judge regressions on the fast-pass numbers, treat ~1.3× alternating inflation with either signature as environment noise, and check the main-thread Running/wait split in the trace (the skill's analyze_startup.py prints it per iteration) before blaming SDK code.
