OTel Engine: java-compat vs otel-kotlin

What the SDK gains at startup by running OpenTelemetry on the pure-KMP otel-kotlin engine instead of the java-compat mode that decorates opentelemetry-java. Tracker item P17; measured at HEAD (9.3.0-SNAPSHOT) on the whole reference fleet. The flag is sdk_config.otel.enable_otel_kotlin_sdk and it currently defaults to off, so this is unshipped headroom.

Provenance — last updated 2026-08-18 06:30, fleet complete. Tables and prose are updated together; if this stamp is current, the words and the numbers agree. Flagship: X32 (2026-08-17). Pixel 3, A14, A01 Core: X33 (2026-08-17/18). Identical design on all four — two git worktrees differing only in the flag, arms switched by alternating fleet_campaign --repo, 12 ABBA-mirrored legs × 20 iterations (6 per arm) per device, untapped, leg as the unit of evidence (cluster bootstrap + cluster permutation). 960 traces, zero failed or poisoned legs across all four devices. Scripts and raw output: claude-output/2026-08-17-x32-engine-artifacts/.

Bottom line: the kotlin engine is faster on every device in the fleet, and it is a major lever everywhere except the flagship. It saves 15–20% of the SDK-init window on the mid and entry tiers — 5 to 15 milliseconds of main-thread blocking — against just 4.3% (0.50 ms) on the Pixel 7 Pro. All four results are statistically supported.

An earlier flagship-only reading of this concluded the engine flip had become "a minor lever". That conclusion was wrong, and this document previously carried it. The flagship is the one device where the work the flip removes has already been optimised into near-nonexistence; taking it as the fleet answer understated the change by a factor of four.

Compat-arm section medians, µs precision. The OTel construction surface spans 4.4 ms on the flagship to 59.3 ms on the Go device — 13.6× — and the window saving tracks it almost monotonically. The engine flip does the same proportional work everywhere (it removes 40–90% of these sections on every device); what differs is how much there is to remove. On the flagship that work has already been optimised to the point where halving it is invisible at the window level, which is exactly why a flagship-only measurement misleads.

The proportional reductions per section are consistent across the fleet: tracer-init −42% to −65%, span-service-init −44% to −58%, logger-init −68% to −90%, and otel-module unchanged everywhere (±7%). That last row is a useful internal control — a section the flip should not touch, and does not.

Propagation was verified per device, not assumedartifact inspection cannot answer this; trace slices can

Build artifacts cannot confirm the flag reached the APK: the class-load marker appears in both arms (the compat config class is referenced on both engine paths), and whole-APK and per-dex hashing are inconclusive because the build is not byte-reproducible — a control pair built from identical config already hashed differently. A hash difference is not evidence here.

Each device therefore had to pass its own propagation gate from trace slices at microsecond precision, before any effect was read: all three mid/entry devices showed −42% to −90% on the OTel construction sections, far above the 25% threshold. The flagship's gate passed only marginally (−13%, −15%, −69%) — its sections are so small that the same proportional change is nearly invisible, which in hindsight was the first clue that it was the unrepresentative cell rather than the answer.

An earlier attempt at this gate used the SDK's own *-duration-ms attributes and had to be discarded: they are integer-quantised, so on a short pilot the lone "shrinking" section had moved exactly one quantisation unit while the window read 22.00 ms in both arms — evidence that would have licensed either conclusion. The analyzer reports propagation unverified rather than no difference when sections fail to separate, because those are opposite conclusions with identical-looking numbers. A free secondary check: the gradle plugin rejects an unrecognised config key outright, so a successful build proves enable_otel_kotlin_sdk was parsed (the runtime short name n fails the build).

Cross-campaign consistencyan unplanned validity check

X33's compat arms are an independent re-measurement of what X30 measured as released 9.2.0 four hours earlier, on different builds (HEAD snapshot vs mavenCentral release) and different campaigns. They agree closely: A14 45.14 vs 45.05 ms, Pixel 3 29.91 vs 31.90, A01 Core 96.17 vs 92.58. The A14 matching to 0.09 ms across two campaigns and two build provenances is a strong signal that the harness and the fleet are behaving.

What this does not explainthe engine is still not why 9.2.0 was fast

isnSdkEnabled() defaults to false at HEAD — the engine has never shipped as a default — so it cannot account for 9.2.0's step (flagship −38.1%, A14 −35.3%, A01 −35.1%, Pixel 3 −25.2% on 9.0.0 → 9.2.0). This is a separate lever stacked on top of that release, and notably the two effects are largest on different devices, so they are not the same mechanism seen twice. The 9.2.0 attribution question — why the Pixel 3 alone lags — remains open, with the ART-generation hypothesis first in line.

What remains unknown

The tail is entirely unmeasured, and cannot now be recovered from these runs. Every window figure on this page is a median; X32 and X33 computed medians only — no p90, no p95. That is a real gap for a change pitched at startup, because the slow launches are the ones users notice, and a median win can in principle coexist with an unchanged or worse tail. It also cannot be filled retroactively: these campaigns were never ingested into the longitudinal store, so only the derived medians were preserved, and the per-launch traces have since been purged. (The version-evolution work reports p90/p95 precisely because those runs went into the store, which keeps every launch's window.) Getting the tail means re-running the A/B — about 45 min per device at the current shape — with the per-launch windows preserved. Worth doing before any default flip, alongside the correctness work below; on the version side the tail moved with the median on every device, so the expectation is favourable, but it is an expectation and not a measurement.

That re-run was attempted on 2026-08-26 (X37) and FAILED — it measured the wrong SDK, and the tail is still unmeasured. The campaign ran cleanly for 22 legs and produced a confident null: on the A14 the engine effect came out at +0.1% at the median (p=0.97), against the −20.4% X33 had measured on that same device eight days earlier. The median was the pre-registered control, and it failed — which is what the control is for.

Diagnosis: the benchmark app pins embrace = "9.1.0" from mavenCentral, so both arms built against the released 9.1.0 SDK rather than the code under test. X32/X33 carried a prerequisite that X37 did not — "HEAD published to mavenLocal as 9.3.0-SNAPSHOT". Two independent confirmations: an arm-vs-arm check on the Pixel 3 (where X33 measured −17.7%) found the two APKs 0.5 ms apart, +2.4%; and X37's pooled A14 level of 61.21 ms lands on the store's 9.1.0 record (63.02 ms), not on 9.2.0 (45.05) or 9.0.0 (69.62). The campaign benchmarked 9.1.0 against itself.

Why the flag produced no effect on 9.1.0 is NOT established, and an earlier version of this note claimed otherwise. It said the shipped 9.1.0 engine path "does not act on" the flag. That is unsupported: at tag 9.1.0 the flag is wired into production — OtelBehaviorImpl.shouldUseKotlinSdk() is consumed by OpenTelemetryModuleImpl — and both the SDK and the plugin have carried the key since 2025-10. Two candidate explanations remain, with opposite implications: (a) the Kotlin engine offers no startup advantage at 9.1.0, and the win X33 measured is a property of post-9.1.0 code rather than of the Kotlin SDK as such — which would be a real and useful finding; or (b) the injection did not take in these builds, making the null an artefact. The evidence does not separate them: the dex payloads differed, but Android builds are not byte-reproducible, so that proves nothing either way. The propagation gate would settle it in one leg, and X37 cannot run it retrospectively because its driver discarded the per-section rows and deleted the traces. Until then the only claim this page makes about 9.1.0 is that X37 measured it by accident.

What this does and does not change. It does not touch the X32/X33 medians on this page: those were built on a locally published snapshot and gated per device on section propagation, and nothing here contradicts them. It does mean the tail remains entirely unmeasured, and that a correct re-run must (a) publish the SDK under test to mavenLocal and repoint the app's version pin, and (b) gate on section propagation — the OTel construction sections dropping 42–90% while otel-module holds within ±7% — which would have caught this before the first leg. Artefact-level checks cannot: Android builds are not byte-reproducible (the same two trees differed by 275 dex byte positions built as a pair, and 11,790 after independent rebuilds), and the on-device verification tap is engine-agnostic by design. Every figure on this page remains median-only.

Everything except startup timing. Only the build-time flag and only the SDK-init window have been exercised, on four devices. Nothing is known about OTLP export parity, processor/exporter contracts, limits enforcement, or the remote-rollout path (pct_enabled). Swapping the OTel engine has a broad behavioural surface, and a config-gated rollout validated by the full integration suite remains the prerequisite for any default flip. This document is a performance input to that decision, and now a considerably stronger one: the case is 15–20% of SDK-init on the tiers where startup actually hurts, not the 4.3% a flagship-only view suggested.
