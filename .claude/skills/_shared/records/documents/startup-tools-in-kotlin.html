Plan · startup-analysis skills · 2026-09-01

Porting the startup-analysis toolchain from Python to Kotlin

Five skills, nineteen Python files, one method of record — rebuilt as one Kotlin module that anyone with the repo can run on a Mac with a single command, and proven against the Python before the Python is deleted.

The decision. One Gradle JVM module in this repo, :startup-tools, with a Clikt dispatcher and one Kotlin file per former Python script, sharing a single core library. Shipped through installDist behind a checked-in tools/startup wrapper that rebuilds incrementally and then runs the tool directly, so the loop is edit file → tools/startup <command>, with a few seconds of compile in between. Nothing to install beyond what building the SDK already requires. Parity is proven by golden fixtures generated from the real stores, a CPython-compatible random number generator so bootstrap and permutation results match bit for bit, and a captured trace set for the Perfetto layer. Along the way the port fixes the defects the inventory found instead of reproducing them, and records every deliberate departure.

Why this shape and not another

The research compared eight approaches — .main.kts, kscript, JBang, Kotlin Notebook, Amper, a compiled Gradle module, Kotlin/Native and GraalVM. Three facts about this codebase decide it.

The Python is stdlib-only and the Gradle build already contains everything the Kotlin needs. Gradle 9.7.1, Kotlin 2.4.10, kotlinx-serialization, the daemon, the build and configuration caches — all present and warmed by normal development. Every scripting option adds a Homebrew install and a second compiler outside Gradle. The compiled module adds nothing.

The tools spend their time in child processes. adb, gradlew -p examples/ExampleApp and trace_processor run for seconds to hours. JVM cold start, around 0.2–0.4 s, is noise against that — which removes the only argument for Kotlin/Native or GraalVM, both of which cost real time in subprocess ergonomics, build minutes and, for GraalVM, arm64-only macOS support. It also means the tool must be launched outside Gradle: ./gradlew run swallows stdin, converts exit codes into exceptions, breaks terminal detection, and would wrap a Gradle daemon around the campaign's own gradlew children.

The statistics need a reproducibility a script cannot test. The method of record is a seeded two-stage cluster bootstrap and a cluster permutation test. Bit-exact parity with the Python is achievable on the JVM — Commons Math 3's MersenneTwister is a verified init_by_array, and CPython's random layer is about eighty lines on top — and it is provable only with a test suite that runs in CI, which a module has and a script does not.

Runner-up, and when to prefer it

.main.kts scripts with shared code via @file:Import, kept beside the SKILL.md files. JetBrains is committed to the format and AndroidX uses it for exactly this kind of utility. Choose it only if the team wants no Gradle wiring, rarely edits the scripts (each edit costs a 3–5 s recompile, and imported files have a stale-cache bug), and accepts having no unit tests. That is not the stated goal, so it is the fallback rather than the plan.

The wrapper

#!/usr/bin/env bash
# tools/startup — rebuild incrementally (warm daemon: seconds), then run the tool directly.
set -euo pipefail
REPO="$(cd "$(dirname "$0")/.." && pwd)"
if [[ -z "${STARTUP_TOOLS_NO_BUILD:-}" ]]; then
  "$REPO/gradlew" -q --console=plain :startup-tools:installDist
fi
exec "$REPO/startup-tools/build/install/startup-tools/bin/startup-tools" "$@"

STARTUP_TOOLS_NO_BUILD=1 skips Gradle when iterating on data only. The tool runs as a plain JVM process with real stdin, real exit codes, and no Gradle daemon wrapped around the campaign.

Build constraints from the repo: do not apply embrace-jvm-conventions (its JVM 11 target, languageVersion 2.0 and warnings-as-errors are for shipped SDK code); apply detekt directly with the repo config and a module baseline; target JVM 17; stay configuration-cache clean, because problems=fail is set repo-wide.

Two improvements the port enables

Pin the Perfetto engine, not the launcher. The current "v46.0" is a Python launcher script that fetches Perfetto v57.2 native prebuilts — so the recorded version does not identify the engine that produced the stored numbers, and the toolchain secretly requires python3. Prebuilt.kt fetches the native binary by URL and sha256 (mac-arm64 98a41b80…, mac-amd64 c0f61397…) and records v57.2. This is a recipe change and is recorded as one; parity on fixtures should be exact, because the launcher was already running v57.2.

Parse each trace once. Ingest runs three separate trace_processor processes per trace — window, signals, health — three full parses. The native binary offers server unix warm sessions with query --remote; WarmSession loads a trace once and runs every query against it. On a 200-trace leg that is about 200 parses instead of 600. The -q path stays as the always-works fallback and the parity oracle.

Delivery mode — how review is scheduled sets the calendar

Session time is about 5–8 days in every Claude-writes mode; what moves is the waiting between phases and where the irreversible risk lands.

modesession timecalendarwhere the risk sits
Human writes20–27 d~3 weeks parallelisedspread through the writing
Claude writes, synchronous review at every gate5–8 d~8–12 d with same-day reviews; ~3 weeks if each review takes a day — latency dominates and it converges on the human numberlow: nothing compounds past a gate
Claude writes, self-validates and moves on; review async and at the end5–7 d~1–1.5 weeks continuous, plus a final review pass and one fix-up roundan undetected error compounds across phases until review

Why async is viable here: the gates are mechanical, not judgment calls — bit-identical bootstrap CIs, an empty differential, matching trace rows. They do not need a human to pass. Where it is not, this session's void campaign is the case study: a check on the wrong thing, then a judgment call past an inconclusive result. Three rules follow:

  1. A gate passes on zero diff or a pre-declared tolerance, never on "close enough." Any unexplained difference blocks the phase and is listed for the reviewer, not resolved unilaterally.
  2. Two synchronous checkpoints remain: the five decisions before phase 0, and a review before phase 7, because deleting the Python is the one step that is expensive to walk back. Everything before it is additive and mechanically gated.
  3. A phase log is written as work proceeds, so the async review reads what was decided and why, not just a diff.

Recommended: the hybrid — async through phases 0–6 under those rules, synchronous only at the decisions and before cutover. Roughly a week and a half of calendar, with review time spent where it has the most leverage. Sync-at-every-gate buys little safety the mechanical gates do not already provide, and costs most of the speed.

Parallelism with subagents — a further 30–40%, not a multiple

What parallelises well: phase 3's twelve file-only commands — one file each, own golden, own differential, so the layout is the partition (3–4 agents × 3–4 commands); phase 2 alongside phase 1's statistics, since it depends only on the CSV helper and repo utilities; phase 4 alongside 3; phase 5's code alongside 3 and 4; and in phase 0 the goldens script, the module skeleton and the fixture copy.

What does not: the core contract (schemas and the core/ API surface) must exist before fan-out and should be written serially by one author so twelve files share one convention; the CPython RNG parity is a single test-fix loop; integration and every gate judgment stay with one reviewer — agents may run the parity suites, no agent decides a diff is acceptable; and device time is serial on hardware regardless of who wrote the code.

Conditions: strict file ownership — no two agents touch one file — and a conventions note written with the core contract (error handling, exit codes, how a command reports a parity failure), with detekt enforcing the mechanical half. Part of the saving is spent on coordination: precise per-agent specs and curating their output. Net: async review is the larger lever (three weeks to a week and a half); subagents take a further day or two off, chiefly in phase 3.

What does not compress in any mode: device time, Gradle build-test cycles, and review — both the critical path and the quality gate. Fast generation does not produce correctness; review does.

Decisions needed before phase 0

  1. Module name and location — startup-tools/ at the repo root beside the embrace-* siblings, or under a tools/ directory. Recommendation: root-level module, wrapper at tools/startup.
  2. Trace fixtures in the repo — commit 3–5 gzipped traces (a few MB) so CI covers the Perfetto layer, or keep all traces out and accept that layer is local-only. Recommendation: commit the minimal set.
  3. Quantile canonicalisation — adopt Type-7 as canonical with legacy_index retained for stored fields, or keep index-based everywhere and document it. Recommendation: the former.
  4. JVM target — 17, matching what developers run, or the conventions' 11. Recommendation: 17.
  5. Where the port log lives — references/port-log.md in the multi-device skill, or a section in each SKILL.md. Recommendation: one file.

What done looks like

A developer clones the repo on a Mac with a JDK, plugs in a device, and runs tools/startup probe, then fleet-campaign, then ingest, then trend — and every number matches what the Python produced on the same inputs, proven by a CI suite rather than by inspection. There is no python3 anywhere in the workflow. The Perfetto engine version in every record is the one that actually ran. Each trace is parsed once. The cluster statistics have one implementation that every report uses. And the two CLI contracts and four documentation errors the inventory found no longer exist.

What the goldens found in the Python

Twenty-six deliberate departures are listed in startup-tools/PORT-LOG.md; five of them are defects that change what stored data means or whether a workflow could ever have run:

  1. signals_present is empty in every real store record. Ingest used the instrument name as the trace-health canary, and no slice is named composed, so no trace was ever judged clean enough to inventory. The port uses emb-modules-init for the composed window. A consequence: all twelve real records are inadmissible to the corpus under the Python's own clean-signals rule.
  2. cell_runner.py could never have completed a cell. Its temperature parser required a comma-split part to start with mValue=, but the first part starts with Temperature{, so it never read a sensor; and its post-run instrument check looked for app-embrace-start, which the harness never emits. Both are fixed and pinned by tests. Running a cell for real found two more: dumpsys thermalservice prints a "Cached temperatures" block of peak values (72.6 °C on an idle Pixel 3) ahead of the HAL's current readings, so a whole-dump scan gates on history rather than the present; and the shell that launches the runner names it on its own command line, so excluding only the runner's pid trips the host-quiet check. The port reads only the HAL block and excludes the runner's ancestors.
  3. variance_analysis.py crashes on the Pixel 7 Pro at 9.2.0 (emb-record-startup is emitted by no trace there; statistics.median([])). The crash is frozen as a golden; the port renders the section as absent.
  4. The recorded trace_processor_version: v46.0 never named the engine — it was the Python launcher, which fetched Perfetto v57.2. The port pins v57.2 directly and records it; a label change for the store.
  5. Nothing wrote the run-metadata.json that ingest required. fleet-campaign now writes it.
