SDK Init Variance — What Moves the Outliers

Samsung Galaxy A14 (SM-A145M) · Android 15 · Embrace SDK 9.2.0-SNAPSHOT, local build from EMBR-13523/hho/startup-profiling · 2026-08-11 · initial per-iteration deep dive over 2 × 20-iteration passes, then verified against a 5 × 50-iteration corroboration campaign (250 cold starts, back-to-back)

The variance is execution speed, not blocking — corroborated at 250-iteration scale — and the external-factor catalogue found the mechanism for the extremes: CPU clocks are pinned at 2.0 GHz in all 250 iterations (clock theories refuted), and the worst outliers coincide with system_server running an ART heap-compaction GC concurrently, saturating the memory bus while our in-order A55 main thread pointer-chases — same clock, collapsed IPC. Outliers split into three classes: system-pressure/GC (all the extremes), main-thread flash IO, and mild cluster-0 residency. persisted-config-load bimodality was corroborated 5-for-5 with zero counterexamples in 245 cached-config launches. The pass-level fast/slow states remain unexplained by any measured factor — leading theory: memory-interconnect DVFS, invisible to cpufreq.

Two distinct scales of variance

Within a pass, the window ranges 34.4–48.4 ms with no contention (worst iteration wait 1.5% of the window). Across passes, medians alternate ~38↔49 ms (the documented fast/slow pass pattern on this device, at flat battery temperature). Both scales show the same signature — elevated Running time, flat IO, flat wait — so they are probably the same mechanism at different granularity: what speed the CPU the main thread runs on is operating at.

The same two sections carry the excess every time — persisted-config-load and span-service-init/otel-tracer-init. These are also the two biggest CPU consumers in the window, which is exactly what a uniform slow-execution effect predicts: every section inflates roughly proportionally, so the big ones show the biggest absolute deltas. And the thread-state data confirms the inflation is CPU-time, not blocking: over the four slowest iterations, modules-init Running time rises 31.8 → 38.3 ms while its IO (D-state) stays ~2 ms and runnable-wait stays < 0.9 ms. Window sections spend essentially zero time sleeping in every iteration.

External-factor catalogue — what's happening on-device during slow windows

Follow-up sweep over all 250 campaign traces cataloguing everything outside SDK code that overlaps the init window: delivered CPU frequency, thread-state/IO, ART runtime work, GC, binder, in-process and other-process CPU, swap. Full tables in campaign-2026-08-11/factors-report.txt.

  • Clocks exonerated. The weighted cpufreq of the CPU the main thread occupied is 2002 MHz in every one of 250 iterations, fast and slow passes alike, and the vendor freq-limit counters show no thermal cap. The clock-state theory is refuted at the kernel-visible level — slowness is an IPC (work-per-cycle) collapse at constant frequency.
  • The strongest correlate of slowness is concurrent system pressure: system_server CPU rate r = 0.65 with window delta (surfaceflinger 0.53, all other processes 0.55). Baseline is 0.30 CPU-ms per window-ms; the seven worst outliers run at 1.17–1.62 — system_server alone burning 1–1.6 cores for the whole window while our main thread waits < 3 ms. The CPU isn't being stolen; the memory subsystem is.
  • The extremes are system_server ART GC compactions. Drill-down into the 73.0 and 70.1 ms windows: Background young concurrent mark compact GC — 46–51 ms of CompactionPhase (HeapTaskDaemon 48–53 ms CPU, ReferenceQueueDaemon 13–16 ms, FinalizerDaemon 8–9 ms, 71–86 ms of binder replies). Heap compaction copies memory at bus speed — the perfect bandwidth hog next to an in-order A55 doing pointer-chasing class loads.
  • Outlier taxonomy (34 iterations > +4 ms): Type A — system-pressure/GC (16, including all 7 extremes, up to +22.5 ms). Type B — main-thread flash IO (7, D/io 4.5–11.2 ms vs 2.4 baseline; worst also re-verified dex for 13.3 ms). Type C — mild cluster-0 residency (11, +4–6 ms, 65–100% cluster-0, no pressure, no IO — mechanism still open; IRQ load on cpu0–3 or per-cluster idle depth are candidates).
  • Cleared: main-thread binder (0 transactions in every window), own-process GC (~0.4 ms), lock contention (<0.2 ms), swap (static 36.8 MB), MemAvailable (flat ~1.18 GB).
  • Pass-level states resist every measured factor: same clocks, same mean pressure, same memory — yet run-time ×1.33 and in-window ART class-load ×1.85 (9.3–9.8 vs 5.3–5.6 ms). Leading theory: memory-interconnect (MIF/bus) DVFS state — a devfreq domain cpufreq counters can't see — persisting per pass and flipping around the reinstall burst. It predicts the observed gradient exactly: pointer-chasing inflates most (×1.85), block-resume sections ×2 (cache refill), hot-loop CPU work least (×1.1). Test: poll /sys/class/devfreq/*/cur_freq during passes.

Hypotheses, and how to prove or disprove them

H1 — Iteration outliers are cluster-clock effectssuperseded — see external-factor catalogue

Final update. The factor sweep measured delivered CPU frequency directly: 2002 MHz in all 250 iterations — the clock version of this hypothesis is dead. What survives is the IPC framing: outliers execute the same instructions with fewer instructions-per-cycle, driven by memory-bus contention (Type A: concurrent system_server GC) and, for the mild Type C tail, an unexplained cluster-0 residency penalty.

Campaign outcome. The CPU-speed mechanism was corroborated — all 34 slow iterations (>+4 ms vs their pass median) across 250 runs show pure Running-time inflation, uncontended, with flat IO. But the specific "cluster 0 is the slow cluster" mapping was refuted by its own falsifier (c): 6 of the 34, including every extreme outlier (58–73 ms windows), ran with 0% cluster-0 residency — e.g. pass 3's 66.7 ms iteration spent 63.9 ms Running on a single cluster-1 CPU with 0.4 ms wait. Cluster-0 placement survives as a consistent secondary penalty: cluster-0-majority iterations were slower in every one of the 5 passes (+1.5 to +4.0 ms mean; per-pass r = 0.28–0.52; pooled r = 0.39, n = 250). Revised statement: the driver is the momentary per-cluster clock state — either cluster can be slow; cluster 0 just is more often.

Original evidence (2×20 passes). Topology verified on-device: 8 identical Cortex-A55s (/proc/cpuinfo part 0xd05 — big/little ruled out), two independent cpufreq domains (policy0 = cpu0–3, policy4 = cpu4–7, both max 2.0 GHz, observed idling at different clocks). In the first fast pass, window duration correlated r = 0.63 with cluster-0 share.

Remaining prove/disprove. The last link is unchanged and now decisive: (a) re-trace with freq atrace polling so cpu_frequency events land in-window and regress run-time on delivered cycles; or (b) lock clocks on a rooted device (./gradlew lockClocks) — variance collapsing to ~±1 ms proves the clock mechanism outright; outliers persisting at locked clocks would mean the SDK does variable work after all.

Prod signal. Per-section duration attributes on the sdk-init span, segmented by device model: if section shares (percentages of the span) are stable while absolute times spread widely within one model, that's the same CPU-speed effect at fleet scale.

H2 — The pass-level 38↔49 ms alternation is the same mechanism in a device-global statecorroborated 5×50

Campaign outcome. Pass medians 51.1 → 38.5 → 50.6 → 40.4 → 50.5 ms — perfect slow/fast alternation at flat battery temperature (29.3–30.4 °C across all 250 iterations), 0/250 contended, and the predicted ratio asymmetry held exactly (pure-CPU 1.09–1.11×, block-resume 1.83–2.40×). New fact: the state persists for an entire 50-iteration pass (~6.5 min) and flips at the pass boundary, tying it to the harness's reinstall/setup cycle rather than any within-pass periodicity.

Evidence. The slow pass shows uniform Running-time inflation (window run median ~46 vs ~35.5 ms) with 0/20 contended and wait ≤ 1.8% — plus the known asymmetry: pure-CPU sections stay ~1× (span-service-init 15.4 vs 15.3; otel-tracer-init 11.3 vs 12.8) while short block-and-resume sections run ~2× (config-service-init 2.20 vs 0.92, payload-source-init 5.06 vs 2.79, post-init 0.95 vs 0.49). Slower resume latency after brief scheduling gaps points at governor/idle-state behavior, not at any SDK code path.

Prove/disprove. Run 6+ passes alternating back-to-back vs separated by 5-minute idle gaps: if slowness tracks the back-to-back cadence, it's harness-induced device state (each pass reinstalls the APK and hammers the device); if it alternates regardless, it's governor periodicity. Locked clocks (H1c) should eliminate the alternation entirely — that's the decisive test. Battery temperature was already ruled flat in the six-pass campaign.

Prod signal. None needed — prod devices aren't running benchmark passes. The implication for prod is methodological: fleet dashboards should compare percentiles within device-model cohorts, never means across states.

H3 — persisted-config-load is bimodal on first launch: no cached config → ~2 ms; cached config → 7–22 ms of mostly CPU (read + parse)corroborated 5×50

Campaign outcome. 5-for-5 with zero counterexamples: every pass's iteration 0 (fresh install) read the section in 1.35–2.27 ms; all 245 cached-config iterations took 7.27–21.87 ms. The distributions don't touch — cleanly bimodal, exactly as predicted.

Evidence. The 2.43 ms minimum is exactly iteration 0, the first cold start after the pass's fresh install; every later iteration reads the config persisted by its predecessor and costs 7.8–15.3 ms. Thread-state shows the cost is Running (median 8.4 ms) with only ~0.7 ms in IO — so it's deserialization work, not disk.

Prove/disprove on the bench. Pre-seed the config file (adb push before the pass, or run one throwaway launch first): iteration 0 should jump to ~10 ms. Conversely, delete the cached config between iterations: all iterations should drop to ~2.4 ms. Either result isolating the file's presence proves it; if iteration 0 stays fast with a seeded file, the fast path is something else (e.g. a cold-process code path), and this needs re-diagnosis. Cheap instrumentation win regardless: record file size / presence as an attribute on the section.

Prod signal. Segment the section's span attribute by emb.app.version_startup_counter == 1 vs > 1: expect a clean bimodal split. If prod medians for returning users sit near the bench's 10 ms on comparable hardware, the bench number generalizes — and this section (~25% of the window) becomes the top candidate for moving off the critical path or deferring the parse.

H4 — The off-window native sections fluctuate on real IO, and power-service-registration can stall tens of ms on bindercorroborated 5×50

Campaign outcome. The binder stall is not a one-off: power-service-registration exceeded 10 ms in every pass (9 stalls in 250 iterations, max 38.4 ms). The native-lib IO is a stable cost, not noise: load-embrace-native-lib io/D median 2.15–2.40 ms and install-native-crash-signal-handlers 2.80–3.13 ms in all five passes.

Evidence. install-native-crash-signal-handlers (9.4–17.0 ms) and load-embrace-native-lib (6.9–14.7 ms) carry 2–5 ms of D-state/IO — dlopen reading the .so — and their runnable-wait (1–2 ms) is the highest of any section, since they compete with the main thread for cores. power-service-registration is sleep-heavy by nature (median 1.8 ms sleeping — a binder round-trip to system_server) and hit 28 ms once when that call stalled. None of these extend the window directly, but they add scheduler pressure during it.

Prove/disprove. Trace with the binder_driver atrace category and inspect the stalled iteration: the transaction target and system_server's concurrent activity are then visible directly. For the IO: compare a pass with a page-cache-warm .so (consecutive runs) vs after echo 3 > drop_caches (needs root) — or accept it as inherent cold-start IO. In prod, watch the p99 of these sections' attributes; if power-service-registration p99 is tens of ms fleet-wide, consider deferring the receiver registration further or making it async-with-timeout.

What this means for reading benchmarks

  • Judge medians, not maxes, and only on fast passes. The max iteration in a clean pass is a CPU-placement artifact ~90% composed of proportional inflation; it says nothing about SDK code.
  • Normalize iteration 0 or drop it when comparing persisted-config-load: it measures a different code path (no cached config).
  • Section percentages are the portable signal across passes and (per H1's prod check) across devices; absolute ms are hostage to clock state.
  • The two real optimization candidates surfaced by variance analysis are persisted-config-load (defer/offload the parse; ~25% of the window for returning users) and the native-lib IO pair (already off the main thread; verify they never block window sections in prod).
