P17 · otel-kotlin engine · 2026-08-14

The Kotlin OTel engine is faster in the middle and heavier in the tail

Switching the SDK to the otel-kotlin implementation cuts the typical init by 10–15%, and the saving is traceable to three specific OpenTelemetry construction steps. But the outlier picture does not follow the median, and on one device it moves the wrong way.

SUPERSEDED — read the fleet measurement instead (banner added 2026-08-26)

This page is a two-device pilot with one pass per arm. At one cluster per arm, cluster-level inference is not merely underpowered but undefined — the smallest attainable p-value is 1.0 — so nothing here carries a confidence interval. It has been replaced by a proper fleet A/B (12 ABBA-mirrored legs × 20 launches per device, four devices, zero failed legs): OTel Engine — compat vs kotlin.

The median numbers below are superseded and the direction of the conclusion changed. The fleet run measured A14 −20.4%, Pixel 3 −17.7%, A01 Core −15.1%, flagship −4.3%, all supported with intervals. So the effect is roughly larger than this pilot on mid and entry devices, and much smaller on the flagship — the lever is worth 15–20% of SDK-init on the tiers where startup actually hurts.

Every tail statement on this page should be disregarded, as the page itself warns: at n = 50 per arm its p95 rests on three observations and its maximum on one. The tail is being measured properly as of 2026-08-26 (10 legs per arm per device, per-launch windows preserved); until that lands, the honest position is that the engine's effect on p90/p95 is unmeasured, not that it is bad.

What survives, and is worth keeping: the section-localisation table below, and the verification argument in the callout beside it. Establishing that the arms genuinely differ by showing the effect concentrates in exactly the OTel construction sections — while unrelated work stays within a few percent — is a better method than any artefact comparison, and it became the standing "propagation gate" for later engine runs.

What ran

The build-time flag sdk_config.otel.enable_otel_kotlin_sdk toggled between arms — same commit, same app, one config key different. Reference cell (coldStartupBaselineProfile, 50 iterations, CompilationMode.Partial), four legs. Arm order was counterbalanced: compat→kotlin on the A14, kotlin→compat on the Pixel 7 Pro, so thermal drift and install parity cannot masquerade as an engine effect.

Where the time actually goes

The saving is not diffuse. Comparing the SDK's own instrumented sections between arms, the reduction concentrates almost entirely in OpenTelemetry construction while unrelated work barely moves:

This localisation is also what proved the flag took effect

Three attempts to verify the two arms really ran different code all failed: the class-load marker appears in both arms (the class is referenced on both engine paths, so ART verifies it either way), and both whole-APK and per-entry hashing were useless because the build is not byte-reproducible — two builds with identical config already differ. Sections are the SDK's own instrumentation rather than a build artefact, so they sidestep that entirely. Noise cannot concentrate a 55–85% reduction in exactly the OTel construction steps and leave everything else within a few percent.

The outlier picture — where it gets uncomfortable

A median win with a heavier tail is a bad trade, because users experience the tail. Both devices show the Kotlin arm with roughly double the max-to-median ratio of compat, and on the Pixel 7 Pro the p90 is actually slightly worse.

The two devices disagree, and the disagreement is the finding:

  • On the A14 the engine helps the tail too. p90 falls 67.9 → 51.5 ms, and the share of launches slower than the compat p90 drops from 8% to 2%. One excursion reached 91.1 ms, but four in five of the old slow launches simply stopped happening.
  • On the Pixel 7 Pro the tail does not improve, and mildly worsens. p90 goes 17.7 → 17.9 ms and p95 18.1 → 18.9 despite the median falling — and the share of launches slower than the compat p90 rises from 8% to 12%. The engine made typical launches quicker and slow ones slightly more frequent.
  • The relative spread widens on both. max ÷ median roughly doubles (1.37 → 2.10 and 1.23 → 1.99). Whatever the new engine does, its worst case sits proportionally further from its typical case than the old one's did.

This data cannot settle the tail question, and should not be used to

At n = 50 per arm, p95 rests on three observations and the maximum on one; p99 is not supportable at all. A single 91 ms excursion is exactly the kind of event that is indistinguishable from ordinary environmental noise at this sample size — the outlier work on this fleet has repeatedly found that background churn produces excursions of this shape regardless of what the SDK is doing. The median result is solid; every tail statement above is a candidate signal awaiting a properly powered run.

What is being run to settle it

A full-fleet repeat is queued: all four devices (flagship, two mid, entry/Go), both arms, with more iterations per arm so the tail statistics have something to stand on. The entry-tier device matters most here and is absent from the current data entirely — it is the tier where outliers do the most damage, and where the compat engine's OTel construction cost is largest in absolute terms.

What this still does not tell us

  • TTID was not measured — and measuring it would not settle the question anyway. SDK init is 3.8% of end-to-end launch on the Pixel 3 and 1.0% on the A14, so a 15% init win becomes a 0.58% and 0.15% TTID change respectively. Against measured launch-time variability (CV 4.2% and 2.9%) and the clustering in this data, detecting that needs 5,022 iterations per arm on the Pixel 3 (11.7 h) and 33,525 on the A14 (78 h). A realistic 800-iteration arm resolves 1.44% and 1.00% — still 2.5× and 6.7× short. And the confounds are larger than the signal: install parity is worth ±20% on this fleet and heat moved the flagship +31–49%, so more samples cannot rescue it either. TTID wall time can serve as a guardrail (did this make things much worse?), never as evidence that an SDK-init change helped. The cost-re-attribution question — was work removed or merely moved? — should be answered with CPU accounting (main-thread pre-TTID CPU and whole-process CPU), which measures the resource directly and varies far less than wall time. That check has not been run for this change.
  • One run per arm per device. By this project's own standard that is a candidate, not a confirmed result.
  • Only the build-time flag was exercised. Nothing is known about the remote rollout path (pct_enabled), which is how this would actually reach users.
