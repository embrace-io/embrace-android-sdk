External Factors in SDK Startup — Findings Summary

What we are now confident affects SDK-init performance from outside our code, based on several thousand instrumented cold starts across four devices (Pixel 7 Pro / Tensor G2 / Android 15 · Galaxy A14 / Exynos 850 / Android 15 · Pixel 3 / SD845 / Android 12 · Galaxy A01 Core / MT6739 32-bit / Android 10 Go), hot and cool condition arms, per-iteration perfetto trace analysis, and causal manipulation experiments. High-confidence findings only. New to this investigation? Start with the primer: how the SDK starts. Full detail: testing log (scoreboard + every experiment).

How to read the numbers here. This document is about mechanisms, which outlive any release; the figures are illustrations of magnitude, not the claims themselves. So the durable form of every finding is a ratio or a percentage measured within one SDK version across device classes — that comparison holds even as the SDK gets faster underneath it. Absolute millisecond values are given only to convey scale, and each is labelled with the version it was measured on. The strongest evidence of this durability is the tier span itself: the fastest and slowest devices in the fleet sit ≈8× apart at 8.3.0 (20.9 → 177.1 ms) and still ≈8× apart at 9.2.0 (11.5 → 92.6 ms), even though both ends roughly halved. The hardware ordering is a property of the hardware; the absolute numbers are a property of the release.

The unifying model behind everything below: window duration = fixed work ÷ (CPU clock × IPC). Across every device and condition we measured, the term that actually moves is IPC — the effective speed of the memory subsystem. The SDK's init work (class loading, config decode, OTel assembly) is pointer-chasing and memory-bound, so anything that degrades memory-system throughput degrades our startup, even when CPU clocks are provably pinned at maximum.

A. Factors that set baseline startup speedoutside our control · ranked by impact

A1 · ≈8×Device tier: CPU microarchitecture + memory subsystem

Empirical: identical SDK work spans nearly an order of magnitude across the fleet. At 9.2.0 the window medians are 11.5 ms (Pixel 7 Pro) · 32.0 (Pixel 3) · 45.1 (A14) · 92.6 (A01 Core) — a span of 8.0×. The same measurement at 8.3.0 spans 8.5× (20.9 · 43.5 · 75.6 · 177.1). That stability across two releases is the point: the SDK halved its own cost in between, and the tier ratio barely moved, because tier is a property of the silicon rather than of our code.

That it is the same work on every device is verified by the section-share fingerprint. At 9.2.0 the OTel assembly phase takes 33%, 34% and 33% of the window on the Pixel 3, A14 and A01 Core respectively, and the config decode 17–28% — near-identical proportions across a threefold span in absolute window size. Only the hardware changes.

Theoretical: in-order cores (A53/A55) stall on every cache miss; out-of-order wide cores (X1) hide memory latency. Cache sizes and DRAM width scale with tier, and our workload is dominated by exactly the operations these differences hit hardest.

A2 · up to ~1.9×Device temperature — via memory-subsystem throttling, not CPU clocks

Empirical (measured 2026-08-12 on the then-current build; read the ratios, not the absolute values): Pixel 3 dose-response: cool passes ran 31.9 → 42.2 ms — +32% — as the device self-heated 30→39 °C at exactly 2803 MHz delivered CPU clock in every window; the hot arm (41 °C battery ≈ 70 °C silicon, read via dumpsys thermalservice) ran 50–61 ms at the same clocks. Cool also collapsed the outlier rate (5/250 vs 54/250 slow iterations). The Pixel 7 Pro was indifferent across 28–34 °C — modern headroom absorbs it. Records: cooldown-2026-08-12/pixel/, clock tables in probes-2026-08-12/.

Theoretical + architectural: thermal governors throttle DDR/bus/cache clocks before (and invisibly to) cpufreq — the Pixel 3's HAL literally registers thermal-devfreq-0 as a cooling device. Same clock + hotter silicon = fewer instructions per cycle for memory-bound work.

A3 · +24–40%Ambient device load (how busy the phone already is)

Empirical — causal: inducing system_server churn while launching inflated cold starts +40% on the A14 (758→1058 ms) and +24% on the Pixel 7 Pro (208→258 ms) under identical load, with instant recovery when the load stopped (probes-2026-08-12/). Observationally, the Pixel 3's pass medians tracked its rising background activity (Photos/GMS/Play churn) at flat clocks.

Theoretical: concurrent processes don't need to steal our CPU (main-thread scheduler wait stayed <3 ms throughout) — they steal memory bandwidth from the shared bus, and lower-tier devices have the least bandwidth to share.

A4 · shifts sharesOS / ART runtime version

Empirical: class-loading cost varies by runtime generation — pre-window class-load (embrace-impl-init) is 17.5% of window on Android 12 vs 8% on Android 15 (same silicon tier); ART 10 doesn't even emit per-class instrumentation. Profile-guided AOT never helps within a day: steady state arrives by iteration ~2 (page cache), and the real profile payoff waits for background dexopt (idle + charging), which our data shows cannot fire mid-session.

Theoretical: verification, JIT policy, and AOT state are runtime-owned; the same APK executes meaningfully different runtime work per OS version — and the first day after install runs mostly un-AOT'd.

Refinement — measured (2026-08-12): the SDK ships a baseline profile, but every measurement above ran in the benchmark's fresh-install (verify) state, which never exercised it. The with/without A/B (all four devices) found the profile halves the AOT-less cost where it hurts most: window p50 −42–47% and worst-case −47–52% on A14/A01/P7P, first-launch included. Pixel 3/Android 12 correction (2026-08-13): the earlier "reproducible inversion" did NOT survive a properly counterbalanced re-test — ABBA arms put the boundary deltas at +5.0% and −6.8% (opposite directions, within run-to-run noise), so on ART 12 the profile is neutral: no benefit, no reliable penalty. The original +23% estimate is attributed to residual ordering/thermal bias in the fixed-order design; the prod caveat downgrades from "profile hurts on Android 12" to "profile doesn't help there." Practical upshot: the runtime-version factor is substantially a profile-delivery factor — devices/installs that get profile-compiled code sit near the tier's best case; those that don't pay up to 2×.

A5 · up to 2× window · ±45% TTIDInstall-time compile state — how the app arrived on the device

This was previously filed under "excluded" as a suspected measurement artifact. It is neither excluded nor an artifact — it is the strongest software factor we have measured, and it is promoted here because three separate tests closed it out.

Empirical: the same APK executes as interpreted/JIT code or as AOT-compiled code depending on how it was installed, and the difference roughly halves the window (baseline-profile A/B across all four devices: window p50 −42–47%, worst case −47–52% on A14/A01/P7P). On Samsung the install state alternates between consecutive installs: fast installs show base.apk [status=speed-profile] [reason=install-speg], slow ones [status=verify], producing a +45% swing at TTID scale (cycle medians 597 / 866 / 598 / 863 ms across four fresh-install cycles of 50 plain am start -W launches, no tracing anywhere).

Two theories about it were refuted, which is why the conclusion is now firm. The tracing-overhead explanation died with the untraced E15 test above. The self-oscillator explanation (verify install → JIT writes a profile → next install compiles → verify again) died with a no-launch discriminator: parity alternates perfectly across 8 same-APK reinstalls with zero launches in between, so the state machine is installer-side, not usage-driven. It alternates identically under every SDK version back to 8.3.0 — device behaviour, not ours.

Prod mapping: Play installs carry cloud profiles (install-dm), so production devices land compiled deterministically — meaning the baseline-profile arm is the prod-representative benchmark arm on Play-delivered Samsungs. Benchmarking rule: on Samsung, DEFAULT mode is not a stable verify state; always pair it with the profile arm. There is no public API exposing compile state, which remains the known gap in the shipped device attributes.

B. Factors that cause outlier startupsoutside our control · ranked by observed damage

B1 · +25–60% windowsConcurrent system-process CPU bursts (GC compactions, dexopt, GMS/Play)

Empirical: the strongest outlier correlate on every device. A14: system_server CPU r = 0.73 (n = 250); every iteration with >5 ms of system_server heap-compaction GC overlap was slow (13/13, mean +10.9 ms) — the two worst windows sat under 46–52 ms of active compaction; partial correlation shows GC hurts exactly via the CPU it burns (equal non-GC binder-storm bursts hurt equally). Pixel 3 extremes: dex2oat burning 149–413 ms of CPU inside 100 ms windows. A01 extremes: GMS/sync adapters at 127–245 ms. Made causal by the induced-load experiment (A3). Drill-downs: variance doc §external-factor catalogue; campaign-2026-08-11/factors-report.txt.

Theoretical: heap compaction and dex compilation are memory-copy workloads — the highest bandwidth-per-CPU-second work a phone does. They saturate the DRAM interface precisely while our in-order main thread pointer-chases through class loads and config decode.

B2 · first-launch cohortInstall aftermath — a deterministic trigger for B1

Empirical: the first cold start after an install runs with 2–3× baseline concurrent CPU in every measured pass — and the processes are the install pipeline itself: Play Store 55–80 ms, installd 17–43 ms, artd 48 ms, system_server to 75 ms, plus every app with a PACKAGE_ADDED receiver waking up. Visible three independent ways (factor catalogue, windows net of config, raw P7P launches decaying 468→331 ms over the first minute). Settles by launch ~3. Verification refinement (2026-08-12, 16 passes): the raw iter000 window is not uniformly slow — first launch also skips the persisted-config decode (~2 ms fast path vs 11–26 ms steady-state), and on fast tiers that saved work outweighs the aftermath pressure (iter000/median 0.63–1.18 on P7P/A14/Pixel 3) while the weakest tier still nets slower (A01 +17–39%). Two opposing forces, so in prod judge the counter == 1 cohort by its composition (run-delay + time-since-install attrs separate pressure from work), not by assuming it is slow.

Theoretical: real Play installs are heavier than our adb installs (verification, cloud-profile dexopt), users tap "Open" within the burst, and real apps add their own first-run work (onboarding, migrations, other SDKs) — so prod's first-launch outlier enrichment should exceed the bench's. Prod action: segment version_startup_counter == 1 as its own cohort before any outlier analysis.

B3 · up to 2×Scheduler core placement on heterogeneous silicon

Empirical: rare but catastrophic on big.LITTLE — the two Pixel 3 windows that landed majority-on-little ran 104.3 and 103.1 ms (~2× its median, the two worst non-storm outliers observed). Mild-but-common on the A14's two-domain layout (+2–4 ms, r ≈ 0.3–0.5 in every campaign); benign on the Pixel 7 Pro (mid-core placement costs ~2–3 ms of an 11 ms window).

Theoretical: startup begins before the scheduler has load history for the new process; on asymmetric silicon a wrong initial placement runs the whole window on cores with half the clock and a fraction of the IPC.

B4 · +5–60 msFlash/IO stalls

Empirical: a distinct outlier class with main-thread D-state/IO far above the ~2 ms baseline — up to 61 ms on the A01 (its top outlier correlate, r = 0.73), 50.7 ms in the Pixel 3's worst window (flash contention while dex2oat wrote), 4–11 ms in the A14's Type-B outliers, some with dex re-verification (13 ms of VerifyClass).

Theoretical: cold starts fault code and data in from flash; entry-tier eMMC is slow and its controller is shared, so concurrent writers (installs, sync, logging) turn page faults into multi-ms stalls.

B5 · low-RAM tierMemory pressure: swap, kswapd, and the app's own GC

Empirical: on the 1 GB Go device only: kswapd0 active inside windows (47 ms in the worst), MemAvailable correlates with slowness (r = −0.53), and — a class no other device showed — the app's own ART GC runs 64–99 ms inside half the outlier windows. A third of all A01 iterations qualify as outliers. Records: a01-campaign-2026-08-11/.

Theoretical: at 1 GB with zram, startup allocation itself triggers reclaim and GC; the heap is small enough that init-time allocations cross GC thresholds that bigger devices never notice.

Refuted, retired, and excludedclaims we tested and dropped — kept visible so they are not re-proposed

CPU clock speed per se — exonerated as a primary factor: delivered clocks were pinned at maximum across all 450 A14 and 250 A01 iterations regardless of speed, and near-max on the hot Pixel 3 while it ran 2× slower. (Transient clock dips do contribute mid-tier outliers on SD845, and post-idle ramping costs the P7P ~2 ms — real but minor.)

Charging state — tested directly (A14 full-battery-not-charging arm vs charging arms): no measurable effect at matched temperature.

Core count — rejected as a device-model dimension: every modern tier ships 8, so it has no discriminating power left, and its apparent historical signal was microarchitecture riding along.

The baseline profile "hurts" on Android 12 — refuted 2026-08-13. The earlier reproducible-looking inversion did not survive a counterbalanced re-test: ABBA arms put the boundary deltas at +5.0% and −6.8%, opposite directions and within run-to-run noise. On ART 12 the profile is neutral — no benefit, no reliable penalty — and the original +23% estimate is attributed to ordering/thermal bias in the fixed-order design. The prod caveat downgrades from "profile hurts there" to "profile doesn't help there".

ART generation as the explanation for uneven version gains — argued against 2026-08-25. When one device gained noticeably less than its peers from an SDK release, the oldest-OS-device hypothesis was the natural suspect. Section-level attribution rejects it in that global form: uniformly weaker codegen would depress every phase, yet half the phases improved more on that device, and the shortfall concentrates in a single phase (~79% of it). The effect is phase-specific, not runtime-wide. ART generation remains a real cofactor for compile state (above); it is not a general explanation for cross-device differences.

init-maj-faults as an IO signal — retired as a proxy 2026-08-14. It saturates at both ends of the tier range: pinned at 0 on the Go device even on a cold launch that read 1136 KB and ran ~25% slow (readahead makes the faults minor), and pinned high-and-flat on the flagship, where the cold value sits inside the warm range. It discriminates only on the two middle devices. Use init-disk-read-kb, which separates cold from warm on all four. The general lesson: a proxy can fail by saturating at either end, so check discrimination across the whole tier range rather than correctness on one device.

Section-share drift as a mechanism discriminator — retired 2026-08-16. It survived multiple-comparison correction mechanically and then failed its own premise in both directions. A corrected test can still be the wrong test.

Device load saturation as the cause of entry-tier campaign failures — retracted 2026-08-16. A load average near 20 looked like saturation and prompted a reboot; the same load returned within the hour with six passes running cleanly under it. The real cause is an intermittent ddmlib install-commit timeout on slow eMMC — not thermal either, since it reproduces identically at 44 °C and 55 °C with 8.7 GB free.

A caveat about measuring any of thiswhy a careful benchmark is the wrong instrument for several of these factors

A quiet, well-controlled campaign cannot explain variance — and that is a fact about the design, not about the factors. Joining 28 production attributes to 200 launches found nothing significant at either level, because a cool-gated, settled, single-device run held thermal headroom to a 2.8-point range, available memory to 0.9, and never fired low-memory once. The same attributes correlate strongly when state is deliberately ramped (thermal headroom ρ = +0.55 partialled, p < 0.001). Explanatory power requires the explanatory variable to move, so every factor above was established by inducing the condition — heat, load, install state — rather than by waiting for it to appear in a clean run. The practical consequence is that these factors are best hunted in production data, where the conditions vary on their own, and confirmed in the bench by deliberate manipulation.

One related trap worth naming: "between-pass variance is 93–99% of the total" is a statement about a specific estimator on a specific device and version, not a fleet constant, and it is easily confused with the raw intraclass correlation, which answers a different question and can read 0.027 on the same 200 launches. Both are correct for their own cell. Always say which decomposition a number is, and compute it per arm rather than inheriting it.

The device performance modelliving section — which attributes predict startup performance, and why · revisited at every theory audit

We are deliberately building a causal model, not a correlational one. An attribute earns a place only if it has (1) a mechanistic seat in the unified model (window = work ÷ (clock × IPC), plus wait classes) explaining why it moves performance, (2) demonstrated empirical separation in bench or prod data, and (3) cheap, unrooted collectability. Correlation alone is not admission — core count is the canonical rejection: 2-vs-8 correlates across a decade of devices, but every modern tier ships 8 cores, so it has no remaining discriminating power and its apparent historical signal was really microarchitecture riding along.

p50 and p95 are SDK 9.2.0 on quiet, cool-gated campaigns (200 launches per device, baseline profile applied). "Worst under stress" is deliberately a different kind of number — the worst window seen across all campaigns including heat and induced-load arms, on earlier builds — because that is what the outlier factors on this page actually cost. On the Pixel 3 that gap is the largest in the fleet (35 ms against 120), which is consistent with heat being its dominant factor.

The mechanisms are universal; the damage is tier-dependent. The flagship's worst window still beats the entry device's fastest median — so outlier mitigation matters most exactly where most Android users are.
