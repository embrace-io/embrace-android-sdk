How the Embrace SDK Starts — A Primer

The thing our startup-performance work measures, explained for readers who haven't lived in the code. Everything here is grounded in the SDK's actual init path and in 2,000+ instrumented cold starts across four devices (2026-08). Read this first, then pick your next document from the index below.

This describes SDK 9.2.0, the current published release, and every number below is measured on it — 10 passes × 20 cold launches per device, benchmark build, baseline profile applied. Version matters more than it might seem: 9.2.0 is where two of the phases described below collapsed to a fraction of their former cost, so figures from an earlier release do not describe this one. Where a section name or a structural fact is specific to 9.2.0, it says so.

Where SDK startup sits inside app startup

On a cold start, Android forks a new process for the app, loads its code, and calls the app's Application.onCreate() on the main thread — before any UI exists. Host apps call Embrace.start(context) there, so everything below runs on the main thread, inside the app's own startup, before the first frame. The interval users feel — process start to first visible frame — is called TTID (time to initial display), typically 200 ms–1.8 s depending on device tier. The SDK's init is one slice of that: at 9.2.0, 11.5 ms on a modern flagship, 32 ms on a 2018 flagship, 45 ms on a 2023 entry-tier phone, and 93 ms on a 1 GB Android Go device — roughly 3–6% of TTID across tiers as measured on our deliberately light benchmark app. The SDK's work is essentially fixed per device (a heavier host app doesn't add SDK work — it only adds some concurrent pressure, a bounded effect we've characterized), while TTID scales with the app: real production apps commonly cold-start in 1.5–4 s, so the SDK's realistic share there is more like 1–3%, with the bench share close to a worst case.

Why the main thread, and why up front? Deliberate: the SDK's configuration decides how everything else in the SDK behaves (and the SDK wants to observe the app from as early as possible), so its core init is a hot-path dependency — the work can be made faster or overlapped, but not skipped or deferred wholesale.

The measured interval: "the window"

The SDK instruments its own init with named trace sections (emb-*), visible in any perfetto system trace. As of 9.2.0 the outermost, emb-sdk-start, wraps the whole Embrace.start() call and matches the SDK's exported emb-embrace-init span to within a millisecond.

The number our benchmarks report is not that section, and the difference matters when comparing releases. emb-sdk-start does not exist before 9.2.0, so a metric defined on it could not reach back across the version history at all. Our benchmarks instead report a composed window — from the start of emb-modules-init to the end of emb-post-services-setup — because those sections exist in every version we measure. Two consequences worth carrying: the composed window is a subset of Embrace.start() rather than the whole of it (19 instrumented sections lie outside it, some before and most after), so it understates total SDK-init cost; and every figure in this document is that composed window unless stated otherwise.

Two small sections run before the window at class-load time — embrace-impl-init and bootstrapper-init, triggered by the app's first reference to the Embrace class (often an exporter registration before start()).

What happens inside the window, in order

1 · Load the persisted config17–28% of the window

The very first act (persisted-config-load): read the remote configuration saved by the previous launch from disk and decode it. This is the SDK's behavioral switchboard — everything downstream consults it. Two important properties: it's a CPU-bound binary decode, not a disk wait (the file is small; deserialization is the cost); and it's bimodal: on the first-ever launch there is no file, the load no-ops in ~2 ms, and the SDK runs on defaults until the config fetched in the background takes effect next launch.

At 9.2.0 it costs 6.0 ms on the Pixel 3, 13.0 ms on the A14 and 20.8 ms on the A01 Core — and structurally it is the largest single child of the biggest phase on every device measured, which is why it is the top standing optimisation target rather than merely a large number.

2 · Stand up workers and core services6–14% combined; small individually

Worker thread pools are created (workerthread-init), a SharedPreferences prewarm is kicked off on a background thread, and a chain of small module constructions runs: core, config service (also scheduling the background HTTP config fetch), a disable check, then storage, instrumentation, feature, and data-capture modules. Each is typically under a few ms — but these short sections are the ones most inflated (~2×) when the device is busy, because each involves a wait-and-resume (thread creation, lock handoffs) that pays cache-refill costs on resume.

This group is where one half of 9.2.0's win landed. Across the 9.0.0 → 9.2.0 step config-service-init alone fell by 84–93% — on the A01 Core from 22.2 ms to 1.8 ms. Documents written before 9.2.0 describe this phase as a major cost; at 9.2.0 it is not. Note that the config decode in phase 1 did not go away with it — that remains the single largest child of the biggest phase.

3 · Assemble the OpenTelemetry engine33–34% — the biggest cost

span-service-init, dominated by otel-tracer-init: constructing the OTel SDK instance — tracer provider, resource, processors, exporters. Pure main-thread CPU and class loading; the single largest block in the window on every device tier, and at 9.2.0 remarkably uniform as a share — 33%, 34% and 33% on the Pixel 3, A14 and A01 Core respectively, despite a threefold span in absolute window size.

There is known, unshipped headroom here. The SDK can build this engine on either an OpenTelemetry Java implementation or a Kotlin one; 9.2.0 ships the Java-backed path by default. Measured on 9.2.0-era builds, switching to the Kotlin implementation is worth 15–20% of the whole window on mid and entry devices (A14 −20.4%, Pixel 3 −17.7%, A01 Core −15.1%) and only −4.3% on the flagship, whose OTel construction is already small in absolute terms. It is off by default because correctness work — export parity, processor contracts — is not finished, so treat it as a measured opportunity rather than a property of 9.2.0.

4 · Delivery, payload sources, logging, session bookkeeping15–18% combined

delivery-init (persistence/scheduling scaffolding — executors only, threads start lazily), payload-source-init (device/resource/metadata describers; some detail collection is pushed to workers), log-init, and user-session-orchestration-init (loading the previous user-session metadata from SharedPreferences — the first main-thread prefs read, which can wait on the prefs file load).

5 · Start the first session2–5% in the lab; 35–40% in production

post-init, almost all of it start-first-session: the session orchestrator runs the initial session-part transition under a lock. What that costs depends on one piece of on-disk state. If a user session persisted by the previous process is within its inactivity timeout (30 minutes by default) it is restored, nothing is written, and the section takes well under a millisecond. Otherwise a new user session is created and persisted: the metadata is serialized to JSON and written to SharedPreferences on the main thread, the periodic session cacher's thread is started, and a background-startup timer is scheduled. (The session span itself is created earlier, in span-service-init.)

This is the lab-versus-production gap found on 2026-09-03. Every benchmark relaunches within seconds, so every iteration after the first restores and this phase measures ~0 ms. A real cold start comes hours after the last one and takes the create path. On 9.2.0 that path resolved its JSON serializer at runtime, and the first such lookup in a process loads kotlinx-serialization's whole builtin serializer table (~55 classes) plus reflection: 3–5 ms on an uncompiled Pixel 3, 12 ms on a Pixel 7 Pro launch that also lacked its app image, and 15–19 ms at the production p50 on mid-tier devices, where the median post-init is a third of the whole init. The fix passes a static serializer on the write path; the coldStartupBaselineProfileExpiredUserSession benchmark arm now measures the create path deliberately, and the trace-health pass flags a class-load burst inside this section as the regression signature.

6 · Register the instrumentation6–11%

post-services-setup: service registrations plus load-instrumentation — discovering and registering the auto-instrumentation providers (network capture, view tracking, etc.) via a ServiceLoader that R8 rewrites at build time. Ends with startup-tracking hooking the app-startup measurement itself. The window closes here; the app continues its own startup toward first frame.

The other half of 9.2.0's win is here, and it is the larger half: on the 9.0.0 → 9.2.0 step this phase improved 67–85% across devices, falling from 38.1 ms to 5.8 ms on the A01 Core. It is also the one phase where the devices disagree — the Pixel 3 improved 67% against 84% on its peers, and that single gap accounts for roughly 79% of why the Pixel 3 gained least on that step (−29.3%, against −33.7% and −35.2% for the A14 and A01 Core).

The section tree: what nests in what, in what order, and what each should cost

The six phases above are a narrative grouping. This is the literal structure, read from the 9.2.0 init path: every instrumented section, its parent, and its position. It matters for production data because 9.2.0 exports a subset of these sections as attributes on the emb-embrace-init span (and on the private sdk-init span), keyed <section>-duration-ms — integer wall-clock milliseconds, first occurrence of each name, snapshotted the moment init completes. Five rules for reading the attributes against this tree. Parents include their children, so the values never sum to the span: modules-init alone is 83–89% of it, and span-service-init contains otel-tracer-init. The two class-load sections sit outside the span — embrace-impl-init and bootstrapper-init are reported on it but happen before its start stamp, so a span can be shorter than one of its own attributes. The recorded children account for roughly 82–88% of modules-init; the rest is the trace-only module constructions above, which have no attribute. The three top-level sections tile 95–98% of the span; the remaining sliver is call overhead. And the two SharedPreferences sections float: they record the first touch of the store, on whatever thread made it, so a large prefs-first-read is not necessarily main-thread time.

How to use the last column on production data: judge a device's distribution by its shape, not its milliseconds. A span where persisted-config-load is half the total is a config-decode anomaly (a large or pathological cached config); one where span-service-init is under 15% yet the span is long has lost its time to something outside the recorded children — look at init-run-delay-pct (starved) versus init-cpu-pct (ran slow) before blaming a section. Two "worst seen" figures are in the table because they are the sections that carry the tails on a quiet device: start-first-session when the first span's class loading lands on a cold cache, and prefs-first-read when the main thread reaches the preferences before the prewarm has finished loading them. The shares here come from single 20-launch passes; the phase pills above come from 10×20 campaigns over the composed window, which is why the two sets agree in ordering and disagree by a few points.

Alongside the durations, the same span carries the init window's execution context: init-cpu-pct and init-run-delay-pct (the init thread's on-CPU and runnable-but-waiting shares of the window), init-disk-read-kb and init-gc-count (process-wide), and the environment at the moment — seconds-since-boot, seconds-since-install, seconds-since-update, mem-available-pct, low-memory (only when true), thermal-status (only when throttled), thermal-headroom-pct, prefs-file-bytes (the host app's preferences file, which explains prefs-first-read), and, from the release after 9.2.0, init-compile-filter and init-app-image: ART's compiler filter for the app's own dex, read from the oat header of its base.odex. speed-profile means a baseline profile drove compilation and the profiled classes are preloaded; verify is the state after an install or update before background dexopt runs, in which class loading and cold code cost several times more. It splits every duration on the span, and anything measured later in the process, into compiled and uncompiled populations, which the 9.2.0 data could only infer. The recommendations document specifies them; the fleet-validation document grades how well each predicts a slow init.

What runs concurrently, off the main thread

During the window, SDK background threads handle the deliberately-off-path work: loading the native library and installing crash signal handlers (the biggest concurrent chunk, 5–13 ms of real disk IO + CPU), the HTTP config fetch (whose result only applies next launch), the SharedPreferences prewarm, system-service registrations (connectivity, power, thermal), and startup-record bookkeeping. Two things to understand about this concurrency: it's why crash capture is live within a few ms of start even though the window hasn't closed; and on small devices these threads compete with the main thread for cores and memory bandwidth — part of why entry-tier windows inflate under load.

Where the main thread actually blocks

A code audit mapped every wait on the path. In rough order of impact: first-use worker thread creation (creating a thread parks the caller until the child initializes — sits inside three hot sections); a shared lazy-initialization lock that the main thread and the config-HTTP worker can both want (the main thread can park on the worker's monitor — the top-ranked fix target); SharedPreferences loading (first read waits for the XML parse; the prewarm converts a disk wait into a lock wait rather than eliminating it); and the unavoidable config-file read + first-span class loading. Notably absent: no synchronous network, no explicit latches/sleeps, and no main-thread binder calls in the default path.

Three facts make these numbers meaningful. The same two costs dominate on every tier — OTel assembly + config decode is 50–62% of the window — so the workload is identical and only the hardware changes. The window is memory-bound work (class loading, deserialization = pointer-chasing), which is why it degrades under heat, concurrent device activity and weak memory subsystems rather than under "slow CPUs" per se. And compilation state matters enormously: with the shipped baseline profile actually applied (as Play-installed users get), windows are roughly half of the un-compiled numbers — every figure here has it applied.

Glossary

  • Cold start — app process doesn't exist; Android creates it fresh. The only start type our benchmarks measure.
  • TTID — time to initial display: process start → first frame. The user-facing startup number; the SDK window is a slice of it.
  • Window — the interval our benchmarks report: composed from the start of emb-modules-init to the end of emb-post-services-setup. Defined this way because it exists in every version measured, unlike emb-sdk-start, which 9.2.0 introduced. It is a subset of Embrace.start(), so it understates total init cost.
  • SDK-init span — the whole Embrace.start() interval: the emb-sdk-start section (9.2.0+) ≈ the exported emb-embrace-init span.
  • Sections — named emb-* trace slices the SDK emits around each init phase; the unit of our breakdowns. Their nesting and order are in the section tree.
  • Section attributes — 9.2.0+: the duration of each ● section, as <name>-duration-ms on the exported emb-embrace-init span (cold starts) and the private sdk-init span. Parents include children; two are recorded from before the span starts.
  • Baseline profile / AOT — a shipped list of hot methods that Android compiles to native code at install; without it the init runs interpreted/JIT, roughly 2× slower.
  • iter000 / first launch — the first-ever cold start after install: no persisted config (fast-path load) but runs inside the install-aftermath burst (Play/installer activity) — analyzed as its own cohort.
